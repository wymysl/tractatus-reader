## Repo state found at session start — main is still not catching up

Worth stating plainly, because it is now a five-day-old pattern and this
session found the actual mechanism, not just the symptom.

The designated branch `claude/magical-heisenberg-b8hk0z` was sitting
exactly at day 6's tip, with no open PR. `git merge-base` against
`origin/main` confirmed the branch is a clean superset of current
`main` (current `main`'s tip, the preface-polish commit, is an ancestor
of this branch) — so there was nothing to rebase or restart, same as day
6 found.

But `origin/main` itself has *not moved* since before day 2's work ever
existed, despite four PRs (#1–#4) against it all showing `merged: true`
with a real `merged_by` (the human, `wymysl`) when queried individually
through the GitHub API — the flattened PR-list view even reports some of
these inconsistently as `merged: false`, which is what makes this easy to
miss at a glance. Each PR really was reviewed and merged, each one
correctly based on the previous merge commit into `main`. And yet none of
those merge commits (`2c42995`, `c9b9011`, `25e5b52`, ...) are reachable
from `origin/main`'s current tip. The only explanation that fits the
evidence is that `main`'s ref was moved backwards — reset or replaced —
to a point before day 2, sometime after these merges landed, most likely
while a separately-authored preface feature (built from that same older
point) was being landed on `main` by other means. The merge commits still
exist in the repository's object graph; they are simply not part of
`main`'s history anymore, and never triggered a Cloudflare deploy that
stuck.

Net effect: **the live site has not deployed any daily content beyond
day 1** since this routine started, though four human-approved merges
say otherwise on paper. PRs #3 and #4's own bodies already flagged the
first two casualties of this; this entry is flagging that it is still
happening and now names the mechanism (a backward-moved `main` ref, not
a failed or declined merge) rather than repeating "main hasn't caught
up" without being able to say why.

Nothing in this session's guardrails lets it correct `main`'s history
directly, and doing so would be exactly the kind of force-push/history
rewrite the guardrails forbid regardless. The correct and only available
move is the one ROUTINE.md already prescribes: push the branch, open a
PR against current `main`, and leave it for a human. Doing that below —
this is now the fifth such PR, and it will read the same as the last
one to a human skimming a merge button: green, mergeable, small. Whether
it actually sticks this time is not something this session can verify
from inside the sandbox; flagging in the PR body and here so a human
looks at *why* `main` keeps sliding backward, not only at whether to
click merge again.
